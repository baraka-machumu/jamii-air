## Decisions taken during Phase 3

| Topic | Decision | Why |
|---|---|---|
| Minimum version (3.12.d) | A 426 `APP_VERSION_UNSUPPORTED` from **any** route raises a gate that is set once and never cleared, and the root layout renders it **instead of the router**, so no screen and no deep link can get behind it. The check runs before the API client's auth-route exit, because the 426 may answer the refresh at launch, and it ends the splash wait. The button is the Play Store page built from the package name; iOS has no store listing yet (Plan 5.0), so the screen shows a note instead of a dead button | App Flow §3.3, TRD API-07; nothing in the app works against an API that refuses the build |
| Accessibility (3.12.c) | The audit found the labels, roles, states and 44 pt targets already in place, so the pass added what was missing: caps on OS font growth (`maxFontScale.text` 1.8 by default, `compact` 1.3 inside anything of a fixed height — pill buttons, input rows, the tab badge, the wordmark), and `Spinner`, which announces itself, for waits that are the whole screen or list. Paging footers stay silent on purpose: content is already on screen and an announcement per page talks over the reading. A sweep test renders Welcome, Sign up and the feed and fails if any reachable control has no name | Design Brief §8; a clipped label and a silent screen are the two failures a phone's accessibility settings actually produce |
| EAS Update (3.12.e) | One channel per build profile (`development`, `preview`, `production`), `runtimeVersion` policy `appVersion`: an update only reaches builds with the same version, so JS can never land on a different native side. The app waits at most 8 s for an update at launch (the same budget as the session restore) and otherwise starts on what it has. `expo-updates` is a native module, so **the dev build on the phone is stale until the next `npm run build:dev`**; dev builds ignore updates anyway, so this is for `preview` and `production` | Plan 3.12; a JS-only fix (like the two from the 3.9 phone session) can then reach installed builds without a rebuild |
| Design tool | The screens were designed on a Claude design canvas, not in Figma (Design Brief §12). The tokens live in `mobile/src/theme/tokens.ts`, checked by tests | One engineer with Claude Code (D-11); the canvas is clickable and was approved as is |
| Navigation | **Expo Router** (file routes in `mobile/src/app/`) instead of hand-wired React Navigation (TRD §3) | It is built on React Navigation, is Expo's default for SDK 57, and gives the deep links (`/p/:id`, `/u/:username`) and typed routes needed in task 3.9. Signed-out and signed-in screens are separated with `Stack.Protected` guards |
| Display font | Nunito ExtraBold, logo and onboarding headlines only | The brief asks for one rounded display face; proposed on the design canvas and approved |
| Tests | jest-expo + React Native Testing Library 13 (Expo Router's `renderRouter` needs the synchronous `render` of v13) | Contrast of every text pair, translation parity and the routing guards are tested from task 3.1 |
| Sentry | Deferred until a DSN exists | Same as the backend (task 2.16): local development only for now |
| API client | `openapi-fetch` with types from `openapi-typescript`; the spec copy (`src/api/openapi.json`) and the types (`src/api/schema.d.ts`) are committed and refreshed with `npm run api:sync` | The app builds without the backend; a changed route or field is a compile error. The generator runs pinned through npx (it needs TypeScript 5, the app uses 6) |
| Error codes | The backend publishes every error code as the enum of `ApiErrorBody` (`ERROR_CODES`); a backend test scans the sources so none is missed, a mobile test checks each has English and Swahili text | Users see a translated message for every failure the API can report (App Flow §13) |
| Web preview | `react-native-web` and `@expo/metro-runtime` added so `npm run web` opens the app in a browser for quick layout checks. Development aid only: the product targets Android and iOS, and the demo still runs on the reference Android | Fast visual feedback while the EAS dev build (task 3.3) is not set up yet |
| EAS profiles | `development` and `preview` build APKs for internal install; `production` builds the store AAB. App version source is `remote` (EAS keeps the build number, `autoIncrement` on production). Update channels wait for task 3.12 (EAS Update) | APKs install straight from the build link on the reference Android; no manual build-number bumps |
| Preview builds and the API | Purely development for now (owner, 2026-10-11): no HTTPS. `preview` builds call the local API over plain HTTP at `EXPO_PUBLIC_API_URL=http://192.168.0.65:3000` (set in `eas.json`). `app.config.ts` enables Android cleartext traffic for every `APP_VARIANT` except `production` (`expo-build-properties`) | A preview build has no dev server to find the API, and Android release builds block HTTP unless allowed. Keeping production locked means the setting cannot leak into a store build |
| Session handling (3.4) | `src/auth/session.ts`: the refresh token in `expo-secure-store` (`AFTER_FIRST_UNLOCK`), the access token in memory. A 401 on any non-auth route triggers **one** shared refresh, then the request is sent again. At launch the splash waits up to 8 s for the refresh, then opens Home offline and lets the refresh land later (it is never abandoned). Log out clears the device at once and tells the server in the background | Refresh tokens rotate and a reused one revokes the whole session (AU-04): parallel refreshes would sign the user out. An abandoned refresh could lose the rotated token the same way |
| After sign-up (3.4–3.6) | Sign-up opens onboarding: step 1 photo and bio (3.5), step 2 Find people (3.6, the newest accounts from `GET /users/search` with an empty query); Continue opens step 3, Notifications (3.10: Turn on or Not now), then Home. The onboarding flag is set with the sign-in (one state update, no flash of the tabs) and is not saved: an app kill mid-onboarding lands on Home | App Flow §4.2: first session only |
| Profile and Settings (3.5) | Settings saved with AsyncStorage (zustand `persist`); the language also goes to the account (`PATCH /me { locale }`, best effort) for push and email text. A new photo applies at once (upload → `PATCH /me { avatarMediaId }`), the text fields on Save; the local photo shows until the server's sizes are READY. Avatars are downscaled to 1080 px (shown at ≤ 320). Notifications row added with 3.10, Blocked accounts and Delete account with 3.11. Settings rows still to come: Terms / Privacy / Contact support (when the pages exist, Plan 5) | Ship what works now; no dead rows |
| People (3.6) | Follow is optimistic through one small store of the user's latest choices (`src/people/follow.ts`) that every screen reads before the cached server value, so search, lists and profiles agree without patching each cache; a failure rolls back and says so; one request per account at a time. Recent searches are the accounts opened from Search (saved on the phone, max 10), cleared on log out with the follow choices. People lists use `FlatList` (short pages of rows); FlashList stays for the feed and grid (3.8). The user profile lives at `/u/[username]`, the share-link path (3.9). The ⋯ menu (Report, Block, Copy link) waits for 3.9 / 3.11 and the posts grid for 3.8 (since done: grid in 3.8; Copy / Share profile link in 3.9) | App Flow §8.1–8.2 |
| Create flow (3.7) | The system photo picker instead of an in-app gallery grid (App Flow §6 draws one): no photo-library permission on Android, no new native module (`expo-media-library`). Crop by dragging only (no pinch zoom: no gesture library in the app yet). A picked photo is first made an upright JPEG ≤ 2048 px (HEIC and EXIF rotation handled), then cropped and saved at quality 85 for upload. One post at a time; the draft (with its Idempotency-Key) is saved on the phone and survives an app kill; uploading or creating when the app stopped becomes "interrupted" with Retry. Retry continues from the failed step (an uploaded photo is not sent again, the post is created with the same key); a server processing failure starts over with a new upload and key. After 5 polls without PUBLISHED the card goes away: the post exists and appears by itself. The draft's files live in the app cache (the OS may clear them under storage pressure) | App Flow §6, §6.1; TRD API-08 |
| Feed (3.8) | Cards show likes, caption and "View all N comments"; the like / comment / share buttons arrive with 3.9. The ⋯ menu: own post → Delete (App Flow §7.4, built here since post detail is); others → "Unfollow @x?"; ⋯ hidden where there is no action yet (Copy link 3.9, Report / Block 3.11). Since 3.9 the ⋯ is always shown (Copy link) and the like / comment / share buttons are on the card. No offline banner yet: it needs a network-status module (`@react-native-community/netinfo`, a new native build); until then offline shows the error / "Couldn't refresh" states and cached pages stay. Post detail lives at `/p/[id]` (the share path, 3.9). A small toast (`showToast`) for confirmations | App Flow §5 |
| Engagement (3.9) | Likes: one small store (`src/engagement/likes.ts`) holds the state shown for posts just tapped, keyed by post, so a card reads only its own entry. The request waits 300 ms after the last tap and is sent only if the final state differs from the server's. When the server answers, the cached post (feed, detail) takes its numbers and the entry goes, after the cache has notified the cards (no flicker). Double-tap only likes (never unlikes); a single tap on the photo opens the post after the 250 ms double-tap window.
